# Q2. 모델은 도구를 어떻게 고르나

## 모델이 보는 것

모델은 도구의 코드를 보지 못한다. 요청에 함께 보낸 **도구 목록(JSON Schema)** 세 가지만 보고 고른다.

- `name`: 도구 이름 (예: `get_weather`)
- `description`: 언제 쓰는 도구인지 설명한 글
- `parameters`: 인자 이름, 타입, 규칙. 1.6부터는 Pydantic 모델의 `model_json_schema()`가 자동으로 만든다(`src/agent_lab/core/tools.py`의 `tool_spec()`). 그래서 `Field(min_length=2, max_length=30)`이 `minLength`, `maxLength`로 그대로 보인다.

이 세 가지와 질문을 보고, 모델은 다음 셋 중 하나를 고른다.
- 도구를 부른다
- 다른 도구를 부른다
- 도구 없이 바로 답한다

## 실험: 도구 선택률 (`scripts/select_test.py`)

질문 10개에 대해 **첫 응답에서** 맞는 도구를 골랐는지 셌다. 순환은 돌리지 않았다.

질문 구성:
- 날씨 3개 → `get_weather`
- 계산 3개 → `calculate`
- 잡담 4개 → 도구 없이 답해야 맞음

calculate 설명은 두 가지로 비교했다.
- 고치기 전: "숫자 계산이나 단위 변환 계산이 필요할 때 쓴다."
- 고친 뒤: "숫자 계산이 필요하면 반드시 이 도구를 쓴다."

측정일: 2026-11-05

| 모델 | 설명 고치기 전 | 고친 뒤 | 틀린 질문 |
|---|---|---|---|
| fast (Groq gpt-oss-20b) | 10/10 (이전 실행에서는 8/10) | 10/10 | 이전 실행: '123 곱하기 45는?', '1024 나누기 8은?'를 도구 없이 직접 계산 |
| smart (Groq gpt-oss-120b) | 10/10 | 10/10 | 없음 |
| local (llama3.2:3b, CPU) | 6/10 | 6/10 | 잡담 4개 전부: '안녕?'·'좋아하는 색이 뭐야?' → get_weather, '파이썬이 뭐야?'·'고마워!' → calculate |

추가 실험 (1.5 고쳐 보기 ③): get_weather 설명을 `"weather tool"`로 줄여도 fast는 10/10이었다.

## 알게 된 것

1. **큰 모델은 이름만으로도 충분히 고른다.**
   설명을 거의 지워도 맞혔다. `get_weather`라는 이름 자체가 설명 역할을 한다. 그래서 도구 이름은 동사+대상으로 분명하게 짓는다.
2. **실패 유형이 모델 크기마다 다르다.**
   - fast는 쉬운 계산을 도구 없이 풀어 버리는 **과소 호출**을 했다.
   - local은 잡담에도 도구를 부르는 **과잉 호출**을 했다.
   - 같은 "선택률"이라도 어느 쪽으로 틀렸는지 따로 봐야 고칠 방법이 정해진다.
3. **description은 과소 호출에는 듣지만 과잉 호출에는 듣지 않았다.**
   - "반드시 이 도구로"는 "써야 할 때 쓰게" 하는 말이다. "안 써도 될 때 쓰지 말라"는 정보는 없어서 local의 6/10이 그대로였다.
   - 다음에 시도할 것: 시스템 프롬프트에 "도구가 필요 없는 질문에는 바로 답한다" 넣기, 잡담을 먼저 걸러 도구 없이 보내기.
4. **한 번의 10문항 실행은 결론을 내기에 작다.**
   - fast는 같은 고치기 전 설명으로 한 번은 8/10, 다른 날은 10/10이었다. 그러니 "설명을 고쳐서 8→10이 됐다"고 단정할 수 없다.
   - 10문항이면 한 문제가 10%p다. 같은 실험을 여러 번 돌려 평균과 범위를 봐야 한다. 이 점은 5단계 평가에서 반복 실행으로 다룬다.

## 이 프로젝트에서 내린 결정

- 도구 선택이 필요한 작업에는 fast 또는 smart를 쓴다.
- local(llama3.2:3b)은 도구 선택을 맡기지 않는다. 임베딩, 분류, 짧은 요약처럼 도구가 없는 작업에 쓴다.
- 도구 설명에는 "언제 쓰는지"와 함께 "언제 쓰지 않는지"도 적는다.
