# Q5. 임베딩과 벡터 DB는 무엇이고 어떻게 썼나

## 한 문장
**임베딩**은 글을 숫자 목록(벡터)으로 바꾸는 것으로, 뜻이 비슷한 글은 숫자도 비슷하게 나온다. **벡터 DB**는 이 벡터들을 저장해 두고, 질문 벡터와 가장 가까운 것을 빨리 찾아 준다.

## 그림으로
```
파일 ──자르기(청킹)──▶ 청크 1,660개 ──임베딩──▶ 벡터(숫자 768개) ──저장──▶ Qdrant
                                                                         ▲
질문 ──────────────────────────────임베딩──▶ 질문 벡터 ── 가장 가까운 5개 ─┘
```
- 청크: 검색 결과로 돌려줄 코드 조각. 방식 B는 함수 하나 = 청크 하나
- 가까움: 코사인 유사도(1에 가까울수록 비슷)

## 내 구성
| 부품 | 선택 | 이유 |
|---|---|---|
| 임베딩 모델 | Ollama `nomic-embed-text` (768차원, CPU) | 무료, 로컬, 한도 없음 |
| 벡터 DB | Qdrant 로컬 모드 (`data/qdrant` 폴더) | 서버·Docker 없이 같은 API, 배포 때도 파일로 옮길 수 있음 |
| 저장 정보(payload) | 경로, 시작·끝 줄, 함수 이름, 종류, 폴더 목록 | 답에 `경로:줄`로 인용하고, 폴더·종류로 범위를 좁히기 위해 |
| 포인트 ID | 경로 + 시작 줄로 만든 고정 UUID | 다시 넣어도 중복이 생기지 않음 |

## 측정한 것
| 항목 | 결과 |
|---|---|
| 청크 수 | 방식 A(60줄 고정) 505개, 방식 B(함수·클래스 단위) 1,660개 |
| 색인 시간 (CPU) | A 약 11분, B 약 14분. 증분 색인(파일 하나 수정) 8.5초 |
| 검색 recall@5 (개발용 20) | A-벡터 7, B-벡터 10, B-벡터(접두어 없음) 9, BM25 8, 하이브리드 10 |
| 고친 뒤 | 테스트 코드 제외 11 → 질문을 영어로 바꾸기까지 20/20, 봉인 8/10 |

## 알게 된 것
1. **자르는 방식이 검색을 바꾼다.** 함수 단위(B)가 고정 크기(A)보다 3문제 더 찾았다. 함수 하나가 의미 단위이기 때문이다.
2. **임베딩 모델의 언어가 중요하다.** 한국어 질문은 유사도가 0.54~0.55에 다 몰려 사실상 아무거나 나왔다. 같은 뜻을 영어로 물으면 정답이 0.77로 1위였다. 모델이 영어 위주로 학습됐고 코드도 영어이기 때문이다.
3. **정확한 이름에는 키워드 검색이 필요하다.** `DEFAULT_MAX_REDIRECTS` 같은 이름은 벡터보다 BM25나 grep이 정확하다. 그래서 둘을 RRF(순위만 보고 합치기)로 섞은 하이브리드를 만들었다.
4. **입력 길이 상한이 있다.** nomic-embed-text는 2048토큰을 넘으면 뒷부분을 경고 없이 잘라 버린다. 청크를 4,000자(약 1,300토큰) 아래로 나눴다.
5. **같은 모델끼리만 비교할 수 있다.** 질문과 문서는 같은 임베딩 모델로 만든 벡터여야 한다. 모델을 바꾸면 색인을 처음부터 다시 만들어야 한다(배포 때 다시 만날 문제).

## 정리
임베딩은 "글자"가 아니라 "뜻"으로 찾게 해 주지만, 모델의 언어·입력 길이·자르는 단위에 따라 결과가 크게 달라진다. 그래서 하나만 믿지 않고 키워드 검색과 섞고, 검색 품질을 수치로 따로 잰다.
