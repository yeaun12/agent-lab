# Q4. RAG와 파인튜닝은 언제 무엇을 쓰나

## 한 문장
**RAG**는 질문할 때마다 관련 문서를 찾아 모델에게 함께 건네주는 방식이고, **파인튜닝**은 모델 자체를 추가로 학습시켜 지식이나 말투를 몸에 배게 하는 방식이다.
새로 바뀌는 지식을 근거와 함께 답해야 하면 RAG, 정해진 형식·말투·작업 방식을 모델에 익혀야 하면 파인튜닝이 맞다.

## 비교
| | RAG | 파인튜닝 |
|---|---|---|
| 지식을 넣는 곳 | 바깥 색인(벡터 DB) | 모델 가중치 |
| 지식이 바뀌면 | 바뀐 파일만 다시 색인 | 다시 학습 |
| 근거 제시 | 찾은 조각의 `경로:줄`을 그대로 인용 | 어디서 배운 건지 알 수 없음 |
| 필요한 것 | 임베딩 모델 + 벡터 DB, CPU로도 가능 | GPU, 학습 데이터, 학습 시간 |
| 약한 곳 | 검색이 틀리면 답도 틀림 | 학습에 없던 최신 내용, 근거 확인 |

## 이 프로젝트가 RAG를 고른 이유 (내 수치로)
1. **코드는 계속 바뀐다.** httpx 파일 하나를 고치면 증분 색인이 그 파일의 18청크만 **8.5초** 만에 다시 넣었다. 전체 색인도 방식 B 1,660청크에 약 14분이다(CPU). 파인튜닝은 코드가 바뀔 때마다 다시 학습해야 한다.
2. **근거가 필요하다.** 코드 질문의 답은 "어디에 있나"가 핵심이라, `httpx/_config.py:246`처럼 줄 번호로 인용할 수 있어야 사람이 확인할 수 있다. RAG는 찾은 조각에 경로와 줄 번호가 붙어 있다.
3. **무료 환경이다.** 이 PC는 GPU가 1GB라 학습을 할 수 없다. RAG는 CPU의 Ollama(nomic-embed-text)와 파일로 저장하는 Qdrant 로컬 모드로 충분했다.

## RAG에서 실제로 문제가 된 것
- **검색이 답의 상한이다.** 처음 하이브리드 검색은 개발용 질문 20개 중 10개만 상위 5개 안에 정답 파일을 찾았다. 못 찾으면 모델이 아무리 좋아도 답할 근거가 없다.
- **언어 차이.** 한국어 질문은 영어 코드와 잘 맞지 않았다. 검색 전에 질문을 영어 검색어로 바꾸고 테스트 코드를 빼자 10/20 → 20/20(봉인 질문 8/10)이 됐다. 모델을 바꾸거나 학습시키지 않고 **검색 쪽을 고쳐서** 올린 것이다.

## 파인튜닝이 맞는 경우
- 답의 **형식**을 항상 지켜야 할 때 (예: PR 리뷰 지적을 항상 정해진 JSON으로)
- 회사 고유의 말투·용어를 익혀야 할 때
- 작은 모델로 특정 작업(분류 등)을 싸고 빠르게 해야 할 때
- 이런 경우에도 지식 자체는 RAG로 넣고, 파인튜닝은 "어떻게 답하나"를 가르치는 데 쓰는 조합이 흔하다.

## 정리
이 프로젝트처럼 **자주 바뀌는 문서에서, 근거를 대며, 무료로** 답해야 하면 RAG가 맞다. 대신 RAG의 품질은 검색이 정한다. 그래서 3.4에서 검색 품질(recall@5, MRR)을 따로 재고, 개발용과 봉인 질문을 나눠 확인했다.
